# Transaction-graph specs

Design: [transaction-graph-design.md](transaction-graph-design.md). Prefix `TXG`.

Transaction graphs are *off* when the final served configuration has no key
`transaction_graph_populations` or its value is exactly an empty list, and *on* for every other
value, which is validated (TXG-CFG-004) before `N`, the list's largest entry, is computed; one function
implements this predicate (TXG-CFG-014). A step's *population* `P` is its number of real rows (stream rows and whole-file
rows together), its *CHUNK count* `K` the number of its CHUNK rows, and its *echo count*
`E = P − K` the number of its other rows (REPLAY, park echo, FLUSH and forced-EOU rows). A step's *row plan* is the ordered list of every row the runner scheduled for model
execution, one per scheduled request at its scheduled position, with its binding, kind, bits and
host-produced vectors; the transaction runs over it, and `P` counts its rows. The *row-failure
path* fails a row at planning (SESS-MODEL-001, SESS-MODEL-002, FILE-PROMPT-007, FILE-QC-010): the
row stays in the row plan at its scheduled position as a *planning-failed row*, bound as a
non-CHUNK row with its planned-rejection bit set, so it counts in `P` and `E` and never in `K`
(TXG-COV-010); the body rejects it (TXG-MASK-006); its output row is the rejected-row output
(TXG-TXN-010); and its request fails alone from the step's planning-failed set (TXG-FAIL-008).
The *rejected-row output* is the projection row the option-off transaction writes for a row whose
status is nonzero. `P_max = min(max_num_seqs, max_num_batched_tokens)` is the largest step population and `H`
the carrier row width. *Plugin-packed input* is input whose every stream unit the plugin's packer built
(the session factory or `buffer_realtime_audio`, SESS-GEOM-001) and whose every whole-file prompt
`get_generation_prompt` built, with no endpoint policy set (SESS-EP-001, FILE-ENG-002). The
*endpoint arguments* are the endpoint history and book pools and the EOU token ID; a transaction
runs with `endpoint_enabled` true exactly when it receives them. A row *carries an endpoint
policy* when its request sets one (endpoint mode 1 in the row plan), and *endpointing* is on for a
row plan when one of its rows carries a policy. The *policy-free endpoint bookkeeping* is what a
transaction with `endpoint_enabled` true does for every row, with or without a policy: it updates
each CHUNK row's endpoint-book `armed` and `has_output` flags from the row's observed output and
stores each fresh row's initialized endpoint pages. A row takes the *forced-EOU path* when, with
`endpoint_enabled` true, it is a non-CHUNK row whose scheduled token is the EOU token and whose
book has no pending echo, an empty queue and an unfinished stream; a *forced-EOU candidate* is a row that
the host marks, from the CPU row plan, as possibly taking that path (TXG-COV-012). The
*component pools* are the state pools core binds (`component_pools`); the *projected resident-pool
views* are the per-role tensors the model's projection forms over them (TXG-VER-001). A *cell* is one captured CUDA graph of the streaming transaction's body and scatters, keyed by
`(geometry, kind, count)` with kind `chunk` or `echo`. *Serving cells* are the cells the serving
capture creates over the serving pools, and the only cells a scheduled step may replay; *profiling
cells* are the temporary cells the profiling capture creates over core's profiling pools, which
`clear_cudagraphs()` releases. `m` is the charged margin's size and `r` its retained charge
(TXG-MEM-004); `Q` and `M` are the qualification and mixed workloads (TXG-QUAL-002, TXG-QUAL-004).
The *option-off transaction* is the streaming
transaction run without cells over the same row plan, and *`B_hook`* is the same engine
configuration with `transaction_graph_populations` absent (the hook configuration with the default
segment arms captured through the hook). The *hook configuration* and the segment arms are
`registration`'s (REG-ENG-005, REG-CARD-008).

A refusal in these specs is a refusal of this release: it holds until transaction graphs for the
refused configuration are specified and measured, and none forecloses capturing a graph through
#67583's capture hook. Deferred (`[D]`) specs are future obligations, excluded from current
conformance.

## Option and configuration checks

- [ ] **TXG-CFG-001**: The model shall read the transaction-graph option only from the served configuration key `transaction_graph_populations`, given as a flat `--hf-overrides` key or stored by an already-translated configuration; transaction graphs shall be off exactly when the key is absent or its value is an empty list, and on for every other value, including a malformed one such as `63`, `"63"`, `true`, `{}` or `null`.
- [ ] **TXG-CFG-002**: Where transaction graphs are on, the set of captured cells shall depend only on the largest entry `N`, and the other entries shall be validated and recorded in the configuration identity without changing any capture (`[63]` and `[1, 31, 63]` capture the same cells).
- [ ] **TXG-CFG-003**: Where transaction graphs are on, `transaction_graph_config_errors` shall return every violated condition of TXG-CFG-004 to TXG-CFG-009, each naming `transaction_graph_populations`, the condition and the rejected value; while transaction graphs are off, it shall return no condition.
- [ ] **TXG-CFG-004**: Where transaction graphs are on, if the value of `transaction_graph_populations` is not a list, contains a value that is not an `int` (a `bool` is not accepted as an `int`), has duplicate entries, or has an entry outside `1 … P_max` (`min(max_num_seqs, max_num_batched_tokens)`), then `transaction_graph_config_errors` shall return the populations condition, and the model shall compute no `N` from that value.
- [ ] **TXG-CFG-005**: Where transaction graphs are on and `num_gpu_blocks_override` is set, if any entry of `transaction_graph_populations` exceeds `num_gpu_blocks_override − 1` (the non-null pages), then `transaction_graph_config_errors` shall return the populations condition.
- [ ] **TXG-CFG-006**: Where transaction graphs are on, if the server's lookahead (`served_lookahead`, REG-LA-001) is not 0 or 1 (80 or 160 ms), including 3 (320 ms, the published checkpoint's default) and the lookaheads 6 and 13, then `transaction_graph_config_errors` shall return the geometry condition naming the lookahead and the remedy `num_lookahead_tokens` 0 or 1 in `--hf-overrides`, and, if `served_lookahead` raises, shall return the geometry condition carrying the raised message instead of raising; this release refuses the other geometries until their cells are specified and measured.
- [ ] **TXG-CFG-007**: Where transaction graphs are on, if `experimental_native_burst` is true, then `transaction_graph_config_errors` shall return the native-burst condition (REG-VAL-008 includes it in startup validation).
- [ ] **TXG-CFG-008**: Where transaction graphs are on, if the encoder arm the model will run (the configured `encoder_execution_arm`, or `eager` when the key is unset) is not `eager-graphed`, or the decoder arm it will run (the configured `decode_dispatch_arm`, or `compact-eager` when the key is unset) is not `dense-graphed`, then `transaction_graph_config_errors` shall return the segment-arm condition naming each such arm and the value it resolved to; the `dense-graphed` encoder is refused by this function and, under the hook configuration, also by REG-ENG-005, and a non-empty `chunk_bucket_graph_populations` is refused under the hook configuration by REG-ENG-005, not by this function.
- [ ] **TXG-CFG-009**: Where transaction graphs are on, if `enforce_eager` is set, then `transaction_graph_config_errors` shall return a condition naming both `transaction_graph_populations` and `--enforce-eager` and stating that core runs no capture hook under `--enforce-eager`.
- [ ] **TXG-CFG-010**: Where transaction graphs are on and `enforce_eager` is not set, the hook configuration's `cudagraph_mode`, compilation-mode and platform conditions (the registration design, Runner configurations) shall be validated by REG-ENG-005 in the configuration hook and by REG-ENG-006 at model-state construction, and `transaction_graph_config_errors` shall not repeat them.
- [ ] **TXG-CFG-011**: `transaction_graph_config_errors` shall be the only implementation of the transaction-graph-specific conditions of TXG-CFG-004 to TXG-CFG-009; startup validation in `verify_and_update_config` (REG-VAL-008) and model-state construction against the final engine configuration (REG-ENG-006) shall both call it.
- [ ] **TXG-CFG-012**: The function `transaction_graph_config_errors` shall live in a module that imports no vLLM.
- [ ] **TXG-CFG-013**: `transaction_graph_config_errors` shall modify no configuration object it is given.
- [ ] **TXG-CFG-014**: The module of TXG-CFG-012 shall define `transaction_graphs_on(hf_config)`, the one implementation of TXG-CFG-001's on predicate, and every component that decides whether transaction graphs are on (the transaction-graph part and `registration`'s checks, hooks, dependency gate and memory contributors) shall call it and shall not test the value of `transaction_graph_populations` itself.
- [ ] **TXG-CFG-015**: Where transaction graphs are on, when `transaction_graph_config_errors` runs while `max_num_seqs` or `max_num_batched_tokens` is not yet resolved, it shall bound the populations of TXG-CFG-004 by the resolved limits only (by none when neither is resolved), and model-state construction (REG-ENG-006) shall apply the full bound `P_max` against the final engine configuration.

## Transaction structure

- [ ] **TXG-TXN-001**: With transaction graphs on or off, the streaming transaction's prepare phase (structural preflight, CHUNK-bucket decode resolution and formation, per-step batch statistics and every host-only check) shall produce every `int64` and `bool` vector the body reads from CPU plan authority, and shall read no device memory and touch no resident page.
- [ ] **TXG-TXN-002**: With transaction graphs on or off, the streaming transaction's body phase shall read host-produced inputs only as device tensors given to it and shall issue no host-to-device copy itself.
- [ ] **TXG-TXN-003**: With transaction graphs on or off, the body's host control flow shall depend only on `endpoint_enabled`, whether the body runs a CHUNK bucket and over how many rows, the row count, the geometry's lookahead and hop, the decode output widths and the evidence-capture flag (the transaction's `capture` argument); it shall have no host branch on whether a step holds file rows or fresh rows, and per-row protocol state (first chunk, final tail, sample count, fresh bit, file bit, planned-rejection bit, per-row cadence) shall be device data.
- [ ] **TXG-TXN-004**: With transaction graphs on or off, the body shall use no variable-length index of fresh or continuing rows and no per-call staging of fresh-row positions.
- [ ] **TXG-TXN-005**: With transaction graphs on or off, the body shall validate the complete scatter plan before its first scatter.
- [ ] **TXG-TXN-006**: The option-off transaction shall run prepare, body and commit in that order over the whole row plan, uploading the host vectors through the model's host staging, and a cell shall be a capture of the same body code on a sub-plan of one row kind.
- [ ] **TXG-TXN-007**: `advance.advance_model_rows` shall be composed of the prepare, body and commit functions and shall keep the interface its callers use: the positional parameters `core`, `input_ids`, `inputs_embeds` and `plan`; the keyword-only parameters `channel_pools`, `time_pools`, `len_pools`, `h_pool`, `c_pool`, `queue_pool`, `book_pool`, `frontend_raw_pool`, `frontend_mel_pool`, `frontend_counter_pool`, `endpoint_history_pool`, `endpoint_book_pool`, `eou_token_id`, `adapter`, `decode_resolver`, `encoder_transition`, `bucket_transition`, `placeholder_id`, `park_id`, `commit_sink`, `capture`, `graph_covers_decode`, `memory_profile`, `staging`, `native_burst_handoff`, `file_carrier_id`, `continuation_id` and `geometry_order`; with no default for `channel_pools`, `time_pools`, `len_pools`, `h_pool`, `c_pool`, `queue_pool`, `book_pool`, `frontend_raw_pool`, `frontend_mel_pool`, `frontend_counter_pool`, `adapter`, `decode_resolver`, `placeholder_id` and `park_id`, the default `False` for `capture`, `graph_covers_decode` and `memory_profile`, and the default `None` for every other keyword-only parameter; and a tensor return.
- [ ] **TXG-TXN-008**: The option-off transaction's commit shall make one reservation, then run the prevalidated predicated scatters, then run the no-fail stage of status, progress and remaining queue counts. If a scatter or the stage raises, the option-off transaction shall cancel the reservation and propagate that exception; if the cancel itself raises, the transaction shall propagate the cancel's exception as worker-fatal, with the original exception as its context.
- [ ] **TXG-TXN-009**: Where transaction graphs are on, a covered step shall make its one reservation before its first cell launch and stage it after its last (TXG-EXEC-010), and its cells shall run the body and the predicated scatters between the two.
- [ ] **TXG-TXN-010**: With transaction graphs on or off, every row of the row plan shall be indexed by its runner-scheduled position: row `i` shall read only the runner's `input_ids[i]`, `inputs_embeds[i]` and binding `i`, and shall write only output row `i`, so that no input or output crosses between rows; the transaction's runner-facing output (the escaped row tensor under transaction graphs) shall have exactly one row per scheduled row, in the runner's order, a planning-failed row's being the rejected-row output.

## Cells

- [ ] **TXG-CELL-001**: Where transaction graphs are on, the model shall capture exactly `2N` cells at the server's geometry, each with `endpoint_enabled` true, so that a replay runs the policy-free endpoint bookkeeping (the rows' `armed` and `has_output` flags and the fresh rows' endpoint pages) exactly as the option-off transaction does: one chunk cell and one echo cell at every count from 1 to `N`, each keyed by `(geometry index, kind, count)`, the geometry index being 0 at 80 ms and 1 at 160 ms.
- [ ] **TXG-CELL-002**: A chunk cell shall replay only CHUNK rows (regular chunks, final tails including an empty final tail, silent chunks, a stream's first chunk and a whole file's first step, fresh and continuing alike), and an echo cell shall replay only non-CHUNK rows (REPLAY label drains, park echoes and FLUSH rows); no cell shall replay a row that carries an endpoint policy or is a forced-EOU candidate, whose step falls back instead (TXG-COV-012).
- [ ] **TXG-CELL-003**: A cell captured at count `k` shall read only the first `k` rows of its kind's section of the step arena and shall write its outputs only at the step positions those rows name.
- [ ] **TXG-CELL-004**: A cell's signature shall cover its kind, count, geometry, the control-token IDs, `endpoint_enabled`, whether any of its rows carries an endpoint policy (`endpoint_policy`) and whether any of its rows is a forced-EOU candidate (`forced_eou`), both false at capture (TXG-COV-012), the evidence-capture flag (the transaction's `capture` argument), the emission adapter's callable identity (`adapter`), the resident pool layouts (address, shape, strides, dtype), the null page's block ID (TXG-MASK-007), the carrier width, the layouts of the step arena, step static inputs and step outputs, and, for a chunk cell, the decode, encoder-transition and bucket-transition callable identities and the lazily bound encoder buffers.
- [ ] **TXG-CELL-005**: A signature shall identify a bound-method callable by `(id(__self__), id(__func__))` and any other callable by `id`, and the dense decode binding and the encoder binding shall keep each callable they hand out (one per graph key, one transition per count) for their lifetime.
- [ ] **TXG-CELL-006**: The decoder tier a chunk cell at count `K` replays shall be the tier the option-off transaction selects for a step with `K` CHUNK rows (the smallest captured tier at least `K`), with the same zero padding of rows `K` to the tier.

## Coverage and fallback

- [ ] **TXG-COV-001**: Where transaction graphs are on, `classify` shall determine from the CPU row plan alone, reading no device memory, the cells a step needs or the reason it has none.
- [ ] **TXG-COV-002**: Where transaction graphs are on, a scheduled step that reaches transaction execution (not an all-failed step, TXG-COV-013) with at least one real row (`P ≥ 1`) in an eligible mode (neither the memory-profile mode nor the native-burst mode) shall be covered exactly when, for every kind it contains, a serving cell at that kind's count holds a graph (the chunk cell at `K` when `K > 0`, the echo cell at `E` when `E > 0`) and its signature equals the step's; an empty step or an ineligible mode is never covered (TXG-COV-006, TXG-COV-007), a graph object lost after classification falls under TXG-EXEC-013, and the population need not be an entry of `transaction_graph_populations`.
- [ ] **TXG-COV-003**: Where transaction graphs are on, when a step that reaches transaction execution (not an all-failed step, TXG-COV-013) is not covered, the model shall run the whole step as the option-off transaction, launching no cell, and shall increment the fallback counter for its `(reason, kind, count)` exactly once: `execute` makes that increment (TXG-EXEC-002), and the caller that runs the option-off transaction adds none.
- [ ] **TXG-COV-004**: Where transaction graphs are on, a step that reaches transaction execution (not an all-failed step, TXG-COV-013) with `K > N` shall fall back with reason `chunk-uncovered`, and otherwise a step with `E > N` with reason `echo-uncovered`.
- [ ] **TXG-COV-005**: Where transaction graphs are on, when a needed cell's structural inputs differ from its captured signature, the step shall fall back with reason `signature`, recording the kind and the differing field, and the first such fallback for each `(kind, field)` in a worker shall log one WARNING naming the field.
- [ ] **TXG-COV-006**: Where transaction graphs are on, a step with a CHUNK row of another geometry, a needed cell that holds no graph, or no real rows shall fall back with reason `multi-geometry`, `uncaptured` or `empty` respectively, without raising. Multi-geometry classification is defensive and shall never authorize execution at another geometry: the declined step runs as the option-off transaction at the server's geometry, whose device geometry status rejects the foreign row. `multi-geometry` is reachable only through a row plan built outside the production planner, which binds every foreign-geometry row, a direct engine client's included, as a planning-failed non-CHUNK row (SESS-MODEL-001, SESS-MODEL-002, FILE-PROMPT-007, TXG-COV-010); `empty` likewise, since the model state runs no transaction for a cleanup-only step (REG-MEM-014) or a step whose every row failed at planning (TXG-FAIL-009).
- [ ] **TXG-COV-007**: Where transaction graphs are on, if `execute` is called for a transaction in the memory-profile mode or the native-burst mode, then it shall replay no cell and shall count the call with reason `memory-profile` or `native-burst`; both reasons are defensive and unreachable (TXG-COV-011, TXG-CFG-007).
- [ ] **TXG-COV-008**: Where transaction graphs are on with `N = P_max`, every scheduled step in an eligible mode (TXG-COV-002) with `1 ≤ P ≤ P_max` rows at the server's geometry whose signatures equal the captured ones shall be covered.
- [ ] **TXG-COV-009**: Where transaction graphs are on, a cell shall replay a step's rows of its kind only when their number equals the cell's count exactly; rows shall never be padded into a cell of a larger count, and an uncovered step's coverage shall never be obtained by loosening the signature comparison.
- [ ] **TXG-COV-010**: With transaction graphs on or off, a row that planning fails (SESS-MODEL-001, SESS-MODEL-002, FILE-PROMPT-007, FILE-QC-010) shall stay in the step's row plan at its scheduled position, bound as a non-CHUNK row with its planned-rejection bit set, and, where transaction graphs are on, classification shall count it in `P` and `E` and never in `K`.
- [ ] **TXG-COV-011**: Where transaction graphs are on, the profile transaction (REG-MEM-002, REG-MEM-016) shall run on a profiling dummy step without calling `execute` (TXG-EXEC-012), and no dummy step shall increment a fallback counter of any reason.
- [ ] **TXG-COV-012**: With transaction graphs on or off, the model's forward shall give every transaction it runs on a real step the endpoint arguments, so that the transaction runs with `endpoint_enabled` true and a row without an endpoint policy takes the forced-EOU path whenever it would in `B_hook`. Where transaction graphs are on, when classification has found every cell a step needs and execution reaches the signature comparison (TXG-EXEC-001), a step with a row that carries an endpoint policy shall fall back with reason `signature` and field `endpoint_policy`, and a step with a forced-EOU candidate with reason `signature` and field `forced_eou` (TXG-COV-005); the host shall mark forced-EOU candidates from the CPU row plan alone, reading no device memory, such that every row that takes the forced-EOU path in the option-off transaction of the same row plan carries an endpoint policy or is a forced-EOU candidate (a candidate need not take that path). A reason classification assigns first (TXG-COV-004, TXG-COV-006, TXG-COV-007) takes precedence; only a direct engine stream client can produce such a step, by setting an endpoint policy or scheduling the EOU token (SESS-EP-001), and file requests run with endpointing disabled (FILE-ENG-002).
- [ ] **TXG-COV-013**: Where transaction graphs are on, a real step whose every row failed at planning (an *all-failed step*, TXG-FAIL-009) shall be a bypass outcome, not an empty step: it shall replay no cell, increment no fallback counter of any reason and add exactly one `(0, P)` entry to the `(K, E)` histogram (TXG-OBS-001); a step that holds both planning-failed and other rows reaches transaction execution and counts its planning-failed rows in `E`, and the inventory stays `2N` cells.

## Execution of a step

- [ ] **TXG-EXEC-001**: Where transaction graphs are on, `execute` shall run, in this order: the failed-latch check; the verification check (TXG-EXEC-015); the process-constant check (TXG-CAP-016); classification, including the mode reasons; the prepare phase over the whole row plan, building both arena sections; the signature of each needed cell; each needed cell's graph object; the arena pack and upload and the static-input copies; allocation of the escaped row tensor `torch.empty((P, H))`; the composite reservation; the chunk cell's launch when `K > 0`, then the echo cell's when `E > 0`; the copy of `rows_step[:P]` into the escaped row tensor, the commit stage and the counters.
- [ ] **TXG-EXEC-002**: Where transaction graphs are on, when `execute` declines a step at classification or at the signature comparison, it shall increment that step's fallback counter and return for the option-off transaction without modifying any resident page or holding a reservation.
- [ ] **TXG-EXEC-003**: Where transaction graphs are on, if an exception other than a delayed device fault (TXG-FAIL-004) occurs in `execute` during classification, the prepare phase, the signature computation, the arena upload and static-input copies, the escaped-row allocation or the composite reservation, then `execute` shall propagate it as the option-off transaction's structural preflight does, with every resident page unchanged, any reservation it holds cancelled and the binding not latched, except that if cancelling the held reservation before the first launch raises, then the binding shall latch and propagate the failure as worker-fatal; not latching shall not be taken to mean that the engine survives the propagated exception.
- [ ] **TXG-EXEC-004**: Where transaction graphs are on, the escaped row tensor shall be allocated before the first launch, owned by the caller and filled from `rows_step[:P]` after the last launch, and it shall survive later steps.
- [ ] **TXG-EXEC-005**: Where transaction graphs are on, the binding shall own, outside the graph pool, one device step arena with a chunk section and an echo section of `N` rows each, holding every `int64` and `bool` per-row vector its kind's body reads (step position, composed block index, fresh bit and initial book row, file bit, geometry, admitted and prior prompt rows, per-row cadence frames, the planned-rejection bit and, in the chunk section, the endpoint mode, threshold and residue frames that the policy-free endpoint bookkeeping reads).
- [ ] **TXG-EXEC-006**: Where transaction graphs are on, each covered step, a step that reaches transaction execution (not an all-failed step, TXG-COV-013), shall pack both arena sections into one of two pinned host buffers and upload the whole arena with exactly one host-to-device copy, and a pinned host buffer shall be rewritten only after the event recorded after its previous upload has completed.
- [ ] **TXG-EXEC-007**: Where transaction graphs are on, before a covered step's first launch, two device copies shall write the step's `input_ids` and `inputs_embeds` into the first `P` rows of the binding-owned `ids_static[P_max]` and `embeds_static[P_max, H]` (`P_max = min(max_num_seqs, max_num_batched_tokens)`, `H` the carrier width), and each cell shall gather its rows from them by the arena's step positions.
- [ ] **TXG-EXEC-008**: Where transaction graphs are on, each cell shall write its rows' projection rows, status, progress and remaining queue counts into the binding-owned `rows_step[P_max, H]`, `status_step[P_max]`, `progress_step[P_max, 3]` and `remaining_step[P_max]` at the rows' step positions by an in-graph `index_copy_`, so that each output is in the row plan's order when the launches finish.
- [ ] **TXG-EXEC-009**: Where transaction graphs are on, the chunk section shall list a step's CHUNK rows, and the echo section its other rows, each in ascending step position.
- [ ] **TXG-EXEC-010**: Where transaction graphs are on, a covered step, a step that reaches transaction execution (not an all-failed step, TXG-COV-013), shall hold exactly one commit reservation covering all `P` rows (the plan's bindings in row order, `progress_step[:P]`, `remaining_step[:P]` and no evidence-capture records), made before the first launch after re-reading the rows' `component_pools` (REG-STATE-004), and staged once, with `status_step[:P]`, after the last launch; it shall never reserve or stage per kind. With transaction graphs on or off, every commit reservation, a covered step's or the option-off transaction's (TXG-TXN-008), shall be resolved by exactly one successful stage or one cancel: a stage that raises before it publishes the reservation to the sink's collection shall leave the reservation cancellable, and a cancel after a successful stage shall be a no-op. A reservation whose cancel raises remains unresolved, and that failure is worker-fatal (TXG-EXEC-003, TXG-FAIL-002, TXG-TXN-008).
- [ ] **TXG-EXEC-011**: Where transaction graphs are on, a whole-file row's envelope (header and one chunk's samples) shall reach the cells only through its carrier row of `inputs_embeds`, written before the transaction by the file row's own host-to-device copy (`transcription`), and shall not be packed into the step arena.
- [ ] **TXG-EXEC-012**: Where transaction graphs are on, a dummy step (one with no `bind_rows` authorization) shall not call `execute` and shall replay no cell.
- [ ] **TXG-EXEC-013**: Where transaction graphs are on, if `execute` cannot obtain a needed cell's graph object after the step was classified as covered, then it shall latch the binding and raise (worker-fatal), launching no cell and running no option-off transaction.
- [ ] **TXG-EXEC-014**: Where transaction graphs are on, `execute` shall issue every device operation of a step (arena upload, static-input copies, launches, escaped-row copy and commit stage) on the runner's current stream and shall create no stream.
- [ ] **TXG-EXEC-015**: Where transaction graphs are on, if `execute` is called before post-warmup verification (TXG-VER-001) has passed in the worker, then it shall raise an error naming `transaction_graph_populations` and the lifecycle defect, without latching the binding, replaying no cell and running no option-off transaction; not latching shall not be taken to mean that the engine survives the propagated error: whether the worker survives it is the environment's choice, not a plugin guarantee.

## Split equivalence and exactness

TXG-EQ-007 to TXG-EQ-010 restate the acoustic transition's 160 ms behaviour, which holds with
transaction graphs off and which the cells must reproduce; they add no requirement on the transition.

- [ ] **TXG-EQ-001**: Where transaction graphs are on, every covered step, of one kind or split, shall equal the option-off transaction of the same row plan bit for bit in every row's projection row, status, progress, remaining queue count and every resident page of its slot, with the outputs compared in row order.
- [ ] **TXG-EQ-002**: For every row plan `R` with CHUNK positions `C` and other positions `O`, the option-off transaction of `R` shall equal, bit for bit at every row (projection row, status, progress, remaining queue count, every resident page), the merge of the option-off transactions of `R|C` and `R|O` (the sub-plans of those rows in ascending order over the same pools), on CUDA and on CPU, at 80 and 160 ms, with endpointing on and off, over: every accepted plan of 1 to 4 rows with every assignment of each row's kind (CHUNK or other), fresh bit and file bit (4,680 plans); every plan of 1 or 2 rows, with every such assignment, in which one row carries each rejection status class reachable for that row's full configuration (kind, fresh bit, file bit); and 500 random plans per geometry and endpointing setting with `P` uniform on 1 … 16 and each row's kind, fresh bit and file bit drawn independently, and its status accepted with probability 3/4, else a rejection class drawn uniformly from those reachable for its full configuration (accepted when none is), by a generator seeded from the preregistered seed list, every failing plan being reported with its seed and plan. Each rejected row shall come from a fixture whose step reports exactly the intended status class. The test shall record the excluded (configuration, status class) combinations, among them a fresh CHUNK row with `ROW_STATUS_QUEUE_NOT_DRAINED` (its initial book has an empty queue) and a fresh non-CHUNK row with a pending-echo `ROW_STATUS_ECHO_MISMATCH` (a fresh row has no armed echo).
- [ ] **TXG-EQ-003**: Where transaction graphs are on, a replay of the cell of each kind at every count from 1 to `N` shall equal the option-off transaction of the same one-kind sub-plan bit for bit, with endpointing off, for sub-plans whose block indices, row orders, prompts and masks differ from the cell's capture rows.
- [ ] **TXG-EQ-004**: Where transaction graphs are on, a covered step, with endpointing off, shall equal the option-off transaction of the same row plan bit for bit (as TXG-EQ-001) in each of these cases: a stream's first chunk among continuing rows; a file's first step; a regular chunk; a silent chunk that emits the continuation token; a final tail with samples; an empty final tail (zero samples, `final_tail` set); a zero-sample file (empty tail, then end); a drain step; the end step as REPLAY and as FLUSH; an armed echo on a file CHUNK row; split steps whose CHUNK and echo rows each mix file and stream rows; and a fresh non-CHUNK row, both when the protocol checks reject it and when they accept it as a park echo.
- [ ] **TXG-EQ-005**: Where transaction graphs are on at 160 ms (lookahead 1), a covered step, with endpointing off, shall equal the option-off transaction of the same row plan bit for bit for: a one-chunk session (fresh and final in one row); a final tail among regular continuing rows; a final chunk followed by REPLAY drains and a FLUSH row as a direct engine client schedules it; and a final tail of 2,560 samples or more, whose row is rejected with `ROW_STATUS_FINAL_OVERSIZE` while the other rows commit, its request then failing alone (SESS-MODEL-003).
- [ ] **TXG-EQ-006**: With transaction graphs on or off, when the recycled resident pages of a step's fresh rows hold sentinel patterns (NaN, ±Inf or random bits), every output and status of the step shall equal the same step run with those pages zeroed; the stored pages of accepted rows shall equal across the two runs, and the resident pages of each rejected row shall equal that run's own pre-step snapshot.
- [ ] **TXG-EQ-007**: With transaction graphs on or off, at 160 ms (lookahead `L = 1`, regular chunk of 16 mel frames and 2,560 samples), each CHUNK row that is not a final tail shall target `(8L + 1) + 16 · seq` = `9 + 16 · seq` frontend frames for its chunk sequence `seq`, and a final-tail row shall ignore its target.
- [ ] **TXG-EQ-008**: With transaction graphs on or off, at 160 ms, a stream's or file's first CHUNK row shall take no mel-tail prefix and drop no pre-encode output, and a continuing CHUNK row shall take the nine-frame mel-tail prefix and drop the configured pre-encode outputs.
- [ ] **TXG-EQ-009**: With transaction graphs on or off, at 160 ms, each CHUNK row's encoder length shall be its own, clamped at zero, and zero when the row produced no new frames.
- [ ] **TXG-EQ-010**: With transaction graphs on or off, at 160 ms, decode shall read at most the first `L + 1` = 2 encoder frames of each CHUNK row.

## Freshness and file masks

- [ ] **TXG-MASK-001**: With transaction graphs on or off, each fresh row shall read its initial state, whatever its recycled page holds: the body shall gather every state tensor whose initial value is zero (encoder, frontend, predictor, replay-queue and endpoint state) from the null page (TXG-MASK-007) for a fresh row and from the row's own page for a continuing row, and shall gather the book row by the row's own page and select, per row, `where(is_fresh, initial, gathered)` as that gather's first consumer, the initial book row holding the blank last label, the admitted prompt and the geometry; every scatter shall name the row's own page.
- [ ] **TXG-MASK-002**: With transaction graphs on or off, a step's fresh and continuing CHUNK rows shall run in its one CHUNK bucket, and, with transaction graphs on, in one chunk cell launch, never split by freshness.
- [ ] **TXG-MASK-003**: With transaction graphs on or off, the body shall evaluate the file-row selects (FILE-ROW-009 and FILE-ROW-011 to FILE-ROW-014, and the continuation emission of FILE-ROW-003 and FILE-ROW-004) on every step, whether or not it holds a file row, as elementwise choices on each row's file bit, with the token IDs FILE-ROW-010 supplies.
- [ ] **TXG-MASK-004**: With transaction graphs on or off, when a step's file mask and fresh mask are all false, the body's outputs, statuses and stored pages shall equal bit for bit those of the stream-only transaction of the same continuing rows.
- [ ] **TXG-MASK-005**: Where transaction graphs are on, a cell shall cover any mixture of whole-file and stream rows of its kind: a file's first step, regular chunk and final tail in a chunk cell, and its drain and end steps (REPLAY or FLUSH) in an echo cell.
- [ ] **TXG-MASK-006**: With transaction graphs on or off, the body shall give every row whose planned-rejection bit is set a nonzero status, whatever its kind, fresh bit, file bit or scheduled token, as an elementwise select on that bit, so that its predicated scatter stores nothing and its pages stay as they were at the start of the step.
- [ ] **TXG-MASK-007**: With transaction graphs on or off, no transaction, cell replay or capture shall store to the null page of any component pool, whatever its rows' kinds, fresh, file and planned-rejection bits and statuses, and a row plan's CUDA-graph padding entries shall not enter the body, so that the null page keeps the zero bytes of core's zeroed pool allocation for the life of the pool.

## Queue counts

- [ ] **TXG-QC-001**: With transaction graphs on or off, the body shall compute every row's remaining queue count after the step, `QUEUE_LEN − QUEUE_HEAD` of the row's proposed label book, as `int32`, and write it into the transaction's per-row remaining-count output at the row's step position (`remaining_step` under transaction graphs).
- [ ] **TXG-QC-002**: Where transaction graphs are on, the composite reservation shall pass the fixed-address device view `remaining_step[:P]`, `int32` of shape `(P,)`, as the commit plan's `queue_counts` (FILE-QC-001), which `reserve` validates by shape and dtype (FILE-QC-002) and `stage` reads without allocating (FILE-QC-003).

## Capture procedure

- [ ] **TXG-CAP-001**: Where transaction graphs are on, while a chunk cell's outer capture is active, every nested encoder and decoder launch site shall see the eager mode through a context variable and run eagerly over its binding's own storage and padding, so the cell records their kernels directly and no nested graph launch.
- [ ] **TXG-CAP-002**: If a host-to-device staging copy is issued while a transaction-graph outer capture is active, then it shall raise.
- [ ] **TXG-CAP-003**: The `eager-graphed` encoder binding shall expose, at each captured count, an uncaptured transition over its own storage, and the `dense-graphed` decoder binding its `uncaptured_decode_fn`, for use by TXG-CAP-001.
- [ ] **TXG-CAP-004**: Where transaction graphs are on, capturing one cell shall run, on core's capture stream: an eager reference of the body on the cell's capture rows that launches the nested segment graphs; three warm-ups and the capture, each with the nested encoder and decoder bindings running eagerly (TXG-CAP-001); and one validation replay; and shall publish the cell only if that replay's outputs equal the reference's bit for bit and, in every component pool, the null page and the cell's capture-row pages `1 … k` (`k` the cell's count, TXG-CAP-005) equal bit for bit their contents in the snapshot the call takes at the start of its transaction-graph part, before the scatter warm-up, otherwise failing the capture (TXG-LIFE-012).
- [ ] **TXG-CAP-005**: Where transaction graphs are on, a cell at count `k` shall be captured on `k` capture rows that use the non-null free pages `1 … k` of each resident pool, carry the server's geometry, alternate their fresh and file bits, and are all rejected by the transaction (a CHUNK capture row by a zero envelope header, `ROW_STATUS_ENVELOPE`; an echo capture row by the stream carrier token, `ROW_STATUS_ROLE_MISMATCH`), so that no page is stored; each capture row's rejection shall not depend on the content of the page it gathers.
- [ ] **TXG-CAP-006**: Where transaction graphs are on, before the first cell of each capture call, the model shall launch, for each component pool, one scatter row with a rejected status that names the pool's first non-null free page.
- [ ] **TXG-CAP-007**: Where transaction graphs are on, each capture call shall capture the chunk cells from count `N` down to 1 and then the echo cells from `N` down to 1.
- [ ] **TXG-CAP-008**: Where transaction graphs are on, the transaction-graph part of a capture call shall reach the state pools only through `StateSlotBindings.startup_pool_access(layer).component_pools` during that call, shall retain no access object after the call, shall store to no page (the null page included), and shall write only binding-owned memory.
- [ ] **TXG-CAP-009**: Where transaction graphs are on, every capture in a capture call shall run on the `stream` core passes, inside `vllm.compilation.cudagraph_pool.capture_pool` with the `graph_pool` core passes, each cell owning one `torch.cuda.CUDAGraph`, and the model shall create no stream and no graph pool of its own.
- [ ] **TXG-CAP-010**: Where transaction graphs are on, before a capture call returns or raises, it shall synchronize the capture stream so that every eager reference, warm-up, capture and validation replay it started has finished.
- [ ] **TXG-CAP-011**: A capture call shall capture no cell while transaction graphs are off, and exactly `2N` cells or raise while they are on.
- [ ] **TXG-CAP-012**: Where transaction graphs are on, the transaction-graph part of the model shall allocate nothing from core's workspace.
- [ ] **TXG-CAP-013**: Where transaction graphs are on, every resident-pool argument that the masked-scatter kernel receives after startup shall have the address, shape, strides and dtype of an argument launched during the serving capture's scatter warm-up or a cell's eager reference, for component pools and projected resident-pool views alike, on covered and fallback steps.
- [ ] **TXG-CAP-014**: Where transaction graphs are on, after startup no scheduled step, whether it replays cells or falls back with reason `chunk-uncovered`, `echo-uncovered` or `signature`, shall perform a compilation or autotuning that core's JIT monitors observe under `jit_monitor_mode` `error`.
- [ ] **TXG-CAP-015**: Where transaction graphs are on, serving reads of nested invocation counters shall be deltas from a baseline taken after startup.
- [ ] **TXG-CAP-016**: Where transaction graphs are on, `execute` shall compare, before classification on every call, the batch-invariant mode, `torch.backends.cuda.matmul.fp32_precision`, `torch.backends.cudnn.conv.fp32_precision`, `torch.backends.cudnn.rnn.fp32_precision` and `CUBLAS_WORKSPACE_CONFIG` with their values at the serving capture, reading no legacy precision getter; if any differs, then it shall latch the binding and raise (worker-fatal), neither replaying nor falling back.

## Capture lifecycle on the hook

- [ ] **TXG-LIFE-001**: When core calls `prepare_execution_memory()`, the transaction-graph part of the model shall allocate nothing.
- [ ] **TXG-LIFE-002**: Where transaction graphs are on, the profiling forward pass (`prepare_step` with `is_profile` true) shall capture and replay no cell.
- [ ] **TXG-LIFE-003**: Where transaction graphs are on, `initialize_state_slots(bindings)` shall record the bindings it receives; serving cells shall exist only from the serving capture on, over the serving bindings current at that capture, and profiling cells only from the profiling capture until `clear_cudagraphs()` returns.
- [ ] **TXG-LIFE-004**: Where transaction graphs are on, when `capture_cudagraphs(profile_only=True)` runs and its entry check (TXG-LIFE-007) passes, the model shall, after the segment graphs (REG-MEM-020), run the scatter warm-up, capture every profiling cell over the profiling pools into the pool core passes, and then allocate the charged margin (TXG-MEM-004).
- [ ] **TXG-LIFE-005**: Where transaction graphs are on, when `clear_cudagraphs()` runs, the model shall release every cell, binding-owned buffer, signature, recorded layout and margin that the profiling capture created, keep the capture record with its profiling figures as host integers, and complete without error when the profiling capture raised or never ran.
- [ ] **TXG-LIFE-006**: Where transaction graphs are on, when `capture_cudagraphs(profile_only=False)` runs, the model shall first, at the call's entry and before the segment-graph part (REG-MEM-022) captures anything, make the entry checks TXG-LIFE-007, TXG-LIFE-008 and REG-MEM-024 in that order, then decide whether a profiling capture was required (TXG-MEM-007), then make the check of TXG-MEM-009; then, after the segment graphs, run the scatter warm-up and capture every serving cell over the serving pools into core's global graph pool with no margin; then make the memory comparison (TXG-MEM-005); and record the plain-value pool layout for post-warmup verification.
- [ ] **TXG-LIFE-007**: An *attempted* serving capture is a `capture_cudagraphs(profile_only=False)` call that passed every check TXG-LIFE-006 makes before its segment-graph part (the last being TXG-MEM-009), whether or not the call then succeeded. Where transaction graphs are on, if `capture_cudagraphs(profile_only=False)` runs while profiling cells exist, or `capture_cudagraphs(profile_only=True)` runs after a serving capture was attempted in the worker, whether or not it succeeded, then the call shall raise at its entry, before the segment-graph part captures any graph, with an error naming `transaction_graph_populations` and the lifecycle defect.
- [ ] **TXG-LIFE-008**: Where transaction graphs are on, if `capture_cudagraphs(profile_only=False)` runs after a serving capture was attempted in the worker (TXG-LIFE-007), whether or not the attempt succeeded (as an elastic expert-parallel reconfiguration would, which REG-ENG-003 refuses, or a retry after a failed serving capture), then the call shall raise at its entry, before the segment-graph part captures any graph, with an error naming `transaction_graph_populations`, stating that recapture over live state pools is not supported, and naming an engine restart as the recovery; the refusal shall propagate as a worker-fatal error and shall leave the binding's failed latch and every existing graph unchanged until `shutdown()`.
- [ ] **TXG-LIFE-009**: Where transaction graphs are on, when `initialize_state_slots` is called after the serving capture with serving bindings whose pool layout equals the layout the serving capture recorded, it shall change nothing; if their layout differs, then it shall latch the binding and raise (worker-fatal); profiling bindings shall take no part in this comparison.
- [ ] **TXG-LIFE-010**: Where transaction graphs are on, when `shutdown()` runs, the model shall release every cell and transaction-graph binding-owned buffer and log the counter summary (TXG-OBS-006), and shall complete without error for a model state whose initialization did not complete or a binding that never captured.
- [ ] **TXG-LIFE-011**: While transaction graphs are off, including under `--enforce-eager`, the transaction-graph parts of `initialize_state_slots`, `capture_cudagraphs`, `clear_cudagraphs`, `post_warmup` and `shutdown` shall allocate, capture, verify and release nothing.
- [ ] **TXG-LIFE-012**: Where transaction graphs are on, if any failure occurs in a `capture_cudagraphs` call after its entry checks pass (in the segment-graph part, in the transaction-graph part, or in the aggregate memory comparison of TXG-MEM-005), then, before propagating it, the call shall measure the graph memory retained so far, discard every serving or profiling cell, binding-owned buffer and margin the call created and every segment graph and segment-graph buffer it created (REG-MEM-017), and synchronize the capture stream, propagating the original error with its diagnostics (TXG-MEM-005, TXG-MEM-010, REG-MEM-017), so that nothing that call created remains captured; the propagated error, its cause and context included, shall hold no reference to the call's tensors or graphs.
- [ ] **TXG-LIFE-013**: Where transaction graphs are on, a cell shall be replayed only by `execute` on a scheduled step, and then only a serving cell after post-warmup verification passed, or by its own capture's validation replay (TXG-CAP-004) on rejected capture rows inside the `capture_cudagraphs` call's startup-access window; no step shall replay a profiling cell.
- [ ] **TXG-LIFE-014**: Where transaction graphs are on, `clear_cudagraphs()`, `shutdown()` and the failure cleanup of TXG-LIFE-012 shall each release the transaction-graph part (cells, binding-owned buffers and, where it exists, the margin) before the segment-graph part (REG-MEM-017, REG-MEM-021, REG-MEM-026).

## Graph memory

- [ ] **TXG-MEM-001**: Where transaction graphs are on, the model shall measure the retained bytes of every span of TXG-MEM-002 and TXG-MEM-004 with `registration`'s one measurement implementation (REG-MEM-027), and shall implement no measurement of its own.
- [ ] **TXG-MEM-002**: Where transaction graphs are on, each capture call shall record in the capture record its call total (the whole call: segment graphs, cells and, for the profiling capture, the margin), its transaction total (from the scatter warm-up to the last cell, excluding the margin), the total of each kind's cells, each cell's incremental growth in capture order, and its transient peak (the allocator's peak reserved bytes over the call, with peak statistics reset at the call's start, less the reserved bytes at its start).
- [ ] **TXG-MEM-003**: Where transaction graphs are on, the capture record shall hold `PYTORCH_CUDA_ALLOC_CONF` (including `expandable_segments`), `CUBLAS_WORKSPACE_CONFIG` and the PyTorch, CUDA and driver versions.
- [ ] **TXG-MEM-004**: Where transaction graphs are on, the profiling capture shall end by allocating, through `registration`'s margin implementation (REG-MEM-027), one device buffer of `m` bytes, one flat amount per call independent of `N` (64 MiB until the first A40 measurement replaces it), held until `clear_cudagraphs()`, and shall record the free-memory readings immediately before and after that allocation (REG-MEM-027) and their difference as the margin's retained charge `r`.
- [ ] **TXG-MEM-005**: Where transaction graphs are on and a profiling capture ran in the worker, if the serving call total exceeds the profiling call total (which includes `r`), by the aggregate comparison of REG-MEM-027, then startup shall fail with an error naming both call totals, `m`, `r`, the excess and the allocator settings, and giving as remedies a fixed `--kv-cache-memory-bytes` that leaves room for the reported serving total, a smaller largest population, or transaction graphs off.
- [ ] **TXG-MEM-006**: Where transaction graphs are on, the capture record shall keep, after `clear_cudagraphs()`, the profiling call's totals, `m`, both raw free-memory readings around the margin, `r`, and, after the serving capture, the absorbed rounding `serving − (profiling − r)`.
- [ ] **TXG-MEM-007**: Where transaction graphs are on, when the serving capture begins, the model shall decide from the worker's effective cache configuration at that moment, by the required-capture predicate of REG-MEM-027, whether a profiling capture was required, and shall record those effective values and the resulting reason in the capture record.
- [ ] **TXG-MEM-008**: Where transaction graphs are on, when no profiling capture ran in the worker and none was required (TXG-MEM-007), the serving capture shall log one WARNING stating that the transaction graphs and segment graphs were not charged to the budget, the reason (the fixed budget value and whether a startup plan set it, the estimate's setting, or the extensible KV cache), the call, transaction and per-kind totals, and that the budget must leave room for them.
- [ ] **TXG-MEM-009**: Where transaction graphs are on, if a profiling capture was required (TXG-MEM-007) and none ran in the worker before the serving capture, then the serving capture shall fail startup at the call's entry, before the segment-graph part captures any graph, with an error naming `transaction_graph_populations` and the configuration that should have run core's graph-memory estimate.
- [ ] **TXG-MEM-010**: Where transaction graphs are on, a failure in a capture call's transaction-graph part shall raise an error chained from the original exception that names `transaction_graph_populations`, its value and `N`; the capture (profiling, before the state pages are planned, or serving); the phase that failed (binding-buffer allocation, scatter warm-up, a cell's eager reference, warm-ups, capture or validation replay, or the margin allocation); the failing cell (geometry label, kind, count) only when the phase belongs to a cell; the totals retained so far and the transient peak; the budget setting (profiled with the estimate, fixed at the given `kv_cache_memory_bytes`, or profiled with the estimate disabled); the allocator settings; and the remedies of TXG-MEM-011, TXG-MEM-012 or TXG-MEM-013 for its case.
- [ ] **TXG-MEM-011**: When a profiling capture of transaction graphs fails, its error shall give as remedies a smaller largest population, a smaller `max_num_seqs`, or transaction graphs off.
- [ ] **TXG-MEM-012**: When a serving capture of transaction graphs fails under a profiled budget, its error shall give as remedies those of TXG-MEM-011, or a lower `--gpu-memory-utilization`, stating that it helps only when the allocated state pages and KV cache fill the budget and leave too little device memory for the capture's transient peak.
- [ ] **TXG-MEM-013**: When a serving capture of transaction graphs fails under a fixed `--kv-cache-memory-bytes`, its error shall give as remedies a `--kv-cache-memory-bytes` smaller by at least the projected remainder, or a remedy of TXG-MEM-011; the projected remainder shall be, for each kind with at least one cell captured in that call, the mean growth of those cells times its cells not yet captured, stated as an estimate, and for a kind with no captured cell the error shall state the estimate as unavailable while still giving the other remedies.
- [ ] **TXG-MEM-014**: Where transaction graphs are on, after the serving capture the transaction-graph execution of a covered step, from `execute` entry through commit staging, shall allocate device memory only for its escaped row tensor, so that across replayed steps the allocator's reserved and allocated bytes change over those spans by no more than those tensors.
- [ ] **TXG-MEM-015**: Where transaction graphs are on, after the serving capture a step's `execute` call, from entry through commit staging, shall read no device memory statistics, call no device or stream synchronize, run no garbage collection and release no allocator cache; waiting on a pinned host buffer's previous-upload event (TXG-EXEC-006) is excepted.
- [ ] **TXG-MEM-016**: The tests of TXG-MEM-014 and TXG-MEM-015 shall measure a file row's envelope preparation (its host-to-device copy and envelope write, TXG-EXEC-011) separately from the `execute` call, identically in the option-on and option-off arms.

## Post-warmup verification

- [ ] **TXG-VER-001**: Where transaction graphs are on, when `post_warmup()` runs, after the segment-graph check (REG-MEM-025), the model shall compare, in this order, with the values recorded at the serving capture and using only plain values and host state: the live `pool_layout(layer)` snapshot (addresses included) and the pools' device against the encoder parameters' device; the projected resident layout per transaction role (component pool, byte offset, shape, strides, dtype); that all `2N` cells hold their graphs, and the callable identities; the address and size of every buffer outside the cells that the graphs read or write (step arena, step static inputs and outputs, model parameters and buffers, nested bindings' scratch); and the process constants of TXG-CAP-016.
- [ ] **TXG-VER-002**: Where transaction graphs are on, if any comparison of TXG-VER-001 fails, then `post_warmup()` shall latch the binding as failed and raise, so that startup fails.
- [ ] **TXG-VER-003**: Where transaction graphs are on, `post_warmup()` shall allocate no device memory, replay no graph and not enlarge core's workspace; it may allocate one bounded host shadow page of the state layout.

## Failure containment

- [ ] **TXG-FAIL-001**: With transaction graphs on or off, a row that the transaction's per-row validation rejects, other than a planning-failed row (TXG-COV-010, TXG-FAIL-008), shall receive a nonzero status and keep its pages as they were at the start of the step while the step's other rows commit, its status shall reach the sink's collection, after which its owner fails its request alone (SESS-MODEL-003 for stream rows; FILE-QC-012 for file rows), and the step shall neither raise nor latch the binding.
- [ ] **TXG-FAIL-002**: Where transaction graphs are on, if any failure occurs from the start of a covered step's first launch through its commit stage (a failed launch, a failure between the two launches, the escaped-row copy or the commit stage), then the binding shall latch, attempt to cancel the step's reservation and propagate the exception, retrying no launch and running neither kind as the option-off transaction.
- [ ] **TXG-FAIL-003**: Where transaction graphs are on, while the binding is latched, every later `execute` call in that worker shall raise an error stating that transaction graphs failed on this worker and a fresh engine is required, launching no cell and running no option-off transaction.
- [ ] **TXG-FAIL-004**: Where transaction graphs are on, if an asynchronous device fault from a replayed step surfaces at a later synchronizing call, then the model shall let it propagate as a worker-fatal error, without retrying, falling back or attributing it to a cell; a delayed device fault that surfaces at the sink's collection, after the stage, shall neither latch the binding nor cancel the staged reservation.
- [ ] **TXG-FAIL-005**: Where transaction graphs are on, when a request in a covered step is aborted after the step's first launch, the model shall not cancel the step's reservation, and the step shall complete its stage and collection.
- [ ] **TXG-FAIL-006**: Where transaction graphs are on, the step outputs (`rows_step`, `status_step`, `progress_step`, `remaining_step`) shall be consumed by the escaped-row copy and the commit stage before the next step's launches, and no graph-pool intermediate shall be read across a replay.
- [ ] **TXG-FAIL-007**: With transaction graphs on or off, each replay or option-off call that uses a nested segment binding's shared scratch shall write the scratch it reads in full before reading it, so that a step's outputs do not depend on scratch content left by an earlier step.
- [ ] **TXG-FAIL-008**: With transaction graphs on or off, the model state shall record each planning-failed row's request in the step's planning-failed set when it plans the step, and `postprocess_state` shall pass every request of that set to `state_slots.fail_requests` together with the step's collected failures, whether or not the sink's collection reports a status for its row, ending each with finish reason `error`, failing no other request on its account and leaving its pages as they were at the start of the step.
- [ ] **TXG-FAIL-009**: With transaction graphs on or off, outside the native-burst mode, when every row of a real step failed at planning and, where transaction graphs are on, the latch check of TXG-FAIL-010 passed, the model state shall run no transaction (neither `execute` nor the option-off transaction), shall return the rejected-row output for each scheduled row in the runner's order, and shall complete the step's failure handling by TXG-FAIL-008 in `postprocess_state`. In the native-burst mode, which runs only with transaction graphs off and whose sampler consumes the payload that the transaction produces, such a step shall run the option-off transaction, which rejects every row by its planned-rejection status (TXG-COV-010), and its failure handling is the same.
- [ ] **TXG-FAIL-010**: Where transaction graphs are on, the model state's step entry shall check the binding's failed latch before it takes the all-failed bypass of TXG-FAIL-009, and, while the binding is latched, shall raise the error of TXG-FAIL-003 for every real step that schedules a row, an all-failed step included, so that only a cleanup-only step (REG-MEM-014) completes after a latch. After the serving capture, an unlatched all-failed step shall take the bypass whether or not post-warmup verification (TXG-VER-001) has passed: the bypass replays no cell and reserves nothing, and the verification check of TXG-EXEC-015 applies only to `execute`.

- [ ] **TXG-OBS-003**: Where transaction graphs are on, each worker's capture record shall hold the configuration identity, the figures and settings of TXG-MEM-002 and TXG-MEM-003 for both captures, the effective cache values and reason of TXG-MEM-007, whether a profiling capture ran and why not, the budget setting, the margin's figures (TXG-MEM-004, TXG-MEM-006), and the capture and verification times in seconds.
- [ ] **TXG-OBS-004**: Where transaction graphs are on, each capture call shall log one INFO line naming the capture (profiling or serving), the cell count, `N`, the call and transaction totals, the transient peak and the capture time.

- [ ] **TXG-OBS-007**: When a transaction-graph binding is built, it shall reset the module-level state it reads (batch statistics), so that a second engine in the same process starts with clean counters.
- [ ] **TXG-OBS-008**: Under a multiprocess engine, `transaction_graph_counters` shall run on the worker through `AsyncLLM.collective_rpc`.

## Calibration

- [ ] **TXG-CAL-001**: The calibration run shall measure U(1), the median host time from the transaction call to the completion of its device work of a one-row continuing CHUNK step on an otherwise idle engine at the server's geometry, as a preregistered microbenchmark in a fresh process using the step rule's procedure (TXG-QUAL-011, TXG-QUAL-013) with a one-row plan: 2 warm-up and 21 counted steps per arm, transaction graphs on (the chunk cell at 1) and off.
- [ ] **TXG-CAL-002**: The calibration run shall also record the step-time ladder `t(P)` with transaction graphs on and off from the step rule's compositions (TXG-QUAL-012).
- [ ] **TXG-CAL-003**: The calibration output shall be one frozen record holding the audio (utterance ID and chunk index), the snapshot rule, the plan and the procedure; U(1) on and off; the ladder; the served replay fraction (the fraction of steps that replayed in the served `Q` run at concurrency `N`, TXG-QUAL-008, on an engine of the same identity); the device; the date; and the configuration identity: checkpoint revision, plugin version, core build, device model, dtype, the process constants of TXG-CAP-016, geometry, segment arms, scheduling mode, `max_num_seqs`, `max_num_batched_tokens` and the value of `transaction_graph_populations`.

## Qualification (acceptance tier 5)

- [ ] **TXG-QUAL-001**: Acceptance tier 5 for transaction graphs shall be met separately at 80 ms and at 160 ms, on an A40 at FP32, on the stage 1 build, with every comparison against `B_hook` (the same engine configuration with `transaction_graph_populations` absent), as defined by its runner flags and not by the README's default serve command.
- [ ] **TXG-QUAL-002**: The qualification workload `Q` shall run independently paced LibriSpeech test-clean streams at the server's geometry, driven at the transaction level for 2,000 steps at each of the concurrencies 1, `⌈N/2⌉` and `N`, with clips in a seeded permutation, each slot playing the next clip and a fresh stream replacing a retired one, each stream starting at its predecessor's retirement time (0 for the first) plus a delay drawn uniformly from `[0, c)` (`c` the chunk duration) by the seeded generator, each chunk offered when its audio would have arrived, the clock advancing by each step's measured option-on duration and jumping to the next arrival when no stream has a schedulable unit, and each step holding every stream that has a schedulable unit.
- [ ] **TXG-QUAL-003**: The qualification driver shall run every step of `Q` and `M` both replayed and as the option-off transaction on a copy of the pools and compare outputs, statuses, progress, remaining queue counts and every page, with the pool copy and the sink's collection outside any timer.
- [ ] **TXG-QUAL-004**: The mixed workload `M` shall hold `N` in-flight requests at the transaction level, `max(1, ⌊N/4⌋)` of them file slots and the rest `Q`'s streams, populations counting stream and file rows together; each file slot shall take the next file when its file retires, until every file has completed and at least 2,000 steps have run, a file being admitted only while every stream slot is occupied; and the files shall be, in order, one with leading and trailing silence, one whose length is a whole number of chunks, a zero-sample file, one shorter than one chunk, then test-clean utterances from the same permutation.
- [ ] **TXG-QUAL-005**: A qualification run's record shall count steps by case, and the run shall be void when `Q` at concurrency `N` has fewer than 200 split steps or fewer than 50 steps with a fresh CHUNK row among continuing CHUNK rows, or `M` has fewer than 100 split steps containing a file row or lacks a step of any case of TXG-EQ-004 other than the fresh non-CHUNK row; a void run shall be reported and the next seed of the preregistered seed list run, an exhausted seed list leaving qualification incomplete, and a mismatch or fallback in a void run shall still be a failure.
- [ ] **TXG-QUAL-006**: On `Q` and `M`, every covered step, of one kind or split, shall equal the option-off transaction of the same row plan bit for bit, the transcripts shall equal the option-off run's, and the run, whose input is plugin-packed, shall record zero fallbacks of any reason.
- [ ] **TXG-QUAL-007**: The qualification shall run steps with `K > N`, steps with `E > N`, and steps with a forced signature mismatch, and each shall record its expected fallback count and outputs equal to the option-off transaction's.
- [ ] **TXG-QUAL-008**: An engine with transaction graphs on shall complete two served runs on plugin-packed input, each paced by the wall clock: one serving `Q`'s streams (concurrency `N`, the same manifest, seed and offsets) on core's `/v1/realtime`, and one holding `N` requests in flight as `M` defines, its streams on core's `/v1/realtime` and its files on the transcription route. Every stream shall reach a final transcript and every file a successful response, and each option-on run shall record zero fallbacks and report its counters, including the `(K, E)` histogram and the replay fraction. At least two preregistered `B_hook` engine startups, otherwise identically configured, shall run the same workloads; the record shall retain every transcript, report per-request transcript agreement separately for streams and files between every pair of runs, baseline against baseline included, and investigate every disagreement, and an unresolved suspected execution defect shall block qualification. Agreement with a `B_hook` run shall be descriptive and shall not establish exactness, which TXG-QUAL-003 and TXG-QUAL-006 govern. Each engine shall also transcribe each of `M`'s files alone on an idle server, and each option-on transcript shall equal the `B_hook` engine's.
- [ ] **TXG-QUAL-009**: No rate, coverage or capacity claim for transaction graphs shall rest on a constructed schedule (aligned phases, filler rows, enumerated compositions or recorded step-rule plans); preregistered microbenchmarks shall claim only the step time of the compositions they construct, and served coverage and capacity claims shall rest on free-running served runs.
- [ ] **TXG-QUAL-010**: The step rule shall run at the transaction level on test-clean audio in one fresh process per population, each capturing the deployed inventory (the `2N` cells of the declared `N`) through the hook under a profiled budget on the A40; a tier 5 pass at a population shall require that inventory to start, and a run with a reduced inventory shall be reported as diagnostic only, ineligible for tier 5, against a `B_hook` process of the same `max_num_seqs` and segment arms.
- [ ] **TXG-QUAL-011**: For each step-rule population and composition, the driver shall run a preregistered prefix that steps `P` streams individually until each CHUNK-row stream has no armed echo, zero remaining queue and a regular next chunk and each drain-row stream has an armed echo and at least one remaining label, snapshot the slots' pages, record one row plan of `K` CHUNK rows and `E` REPLAY drains at evenly spaced step positions among the CHUNK rows, and run that plan on every step of every leg after restoring the snapshot by an in-place copy into the same pool memory on the runner stream, touching only the slots the step's `bind_rows` authorized through TXG-QUAL-026's adapter, with the lifecycle calls, the restore and the collection outside the timer; a rejected row in either arm shall void the leg.
- [ ] **TXG-QUAL-012**: The step rule's one-kind group shall be continuing CHUNK steps (`E = 0`) at populations 1, 31 and 63, and its split group the compositions `(K, E)` = (27, 4) and (16, 15) at population 31 and (55, 8) and (32, 31) at population 63; one-kind echo steps, and FLUSH-row step times by composition from the free-running `Q` runs, shall be reported and not gated.
- [ ] **TXG-QUAL-013**: For each step-rule population and composition, the step rule shall run two blocks, each of legs OFF1, ON, OFF2 in that order, each leg 2 warm-up and 21 counted steps timed by the host from the transaction call to `torch.cuda.synchronize()` after it, ON replaying the cells and OFF running the option-off transaction of the same plan; with `Δ_b = min(median OFF1_b, median OFF2_b) − median ON_b` and `drift_b = |median OFF1_b − median OFF2_b|`, transaction graphs shall be counted material for that population and composition if and only if `Δ_b ≥ max(5 ms, drift_b)` in both blocks.
- [ ] **TXG-QUAL-014**: The step rule's one-kind group shall pass if and only if transaction graphs are material (TXG-QUAL-013) at populations 1, 31 and 63, and its split group if and only if they are material for all four split compositions; each group shall report its own result, and no result shall be pooled across compositions or groups.
- [ ] **TXG-QUAL-015**: As an exception to TXG-QUAL-001's baseline and TXG-QUAL-026's hook-captured-process requirement, a preregistered body non-regression check shall compare OLD (`4cc1381a66cd695966c9e15c561127a854295948`, the newest commit on the qualification branch whose `advance_model_rows` is not composed of prepare, body and commit functions) with NEW (the frozen commit under qualification), at 80 ms and at 160 ms, on the same A40 at FP32, on core build `9c40a6ffd66ce4019ebcc6a0efac126bdbb4f6ee`. Both shall run with transaction graphs and CHUNK-bucket graphs off, under `--enforce-eager`, with the encoder `eager-graphed` and the decoder `dense-graphed`, and each leg's record shall show equal resolved geometry, lookahead and segment arms. All legs shall use the same audio and the step rule's one-kind plans at populations 1, 31 and 63, with TXG-QUAL-011's prefix and restore procedure, TXG-QUAL-013's timer and TXG-QUAL-026's step lifecycle. Two blocks shall each run OLD1, NEW, OLD2 in order, each leg a fresh process with 2 warm-up and 21 counted steps per population. The check shall pass if and only if `median NEW_b − min(median OLD1_b, median OLD2_b) ≤ max(1 ms, |median OLD1_b − median OLD2_b|)` at every population in both blocks. The record shall report each difference, and one ungated bridge block of NEW legs under `--enforce-eager`, the hook configuration and `--enforce-eager` again. Tier 5 shall be claimed only after the check passes on the body that ships.
- [ ] **TXG-QUAL-016**: The feed-to-park measurement `U_api` shall time, through `AsyncLLM` in a multiprocess engine, from before the session factory's `feed` of one unit (a fresh stream's first chunk, not final) to that `feed`'s return at the park, in five brackets of legs OFF1, ON, OFF2, each leg a fresh engine process following a washout leg of its own arm, discarding repeat 0 and counting repeats 1 to 3 (`U` their maximum and `M` their median), with stream open, abort and retirement outside the timer; each timed repeat shall reach exactly one park with no rejection, and for an ON leg the counter reader shall show one more replay of the chunk cell at 1, one more replay of the echo cell at 1 per later step, and no fallback.
- [ ] **TXG-QUAL-017**: The `U_api` gain shall be established if and only if, in all five brackets, `min(U_OFF1, U_OFF2) − U_ON ≥ max(5 ms, |U_OFF2 − U_OFF1|)`; the same inequality holds on each arm's maximum over its 15 counted samples; and, in all five brackets, `min(M_OFF1, M_OFF2) − M_ON − max(5 ms, |M_OFF2 − M_OFF1|) > 0`.
- [ ] **TXG-QUAL-018**: Each qualification run shall freeze, in a dated record before its first counted sample, its scripts and clock; `Q`'s and `M`'s parameters (concurrencies, seed list, clip and file manifests, offset rule, run lengths, file admission, idle-clock rule, minimum case coverage); the step rule's prefix, snapshot rule, plans, compositions and aggregation; the body non-regression check with its OLD and NEW commits, each leg's runner configuration and overrides, and adapter identity; `U_api`'s procedure and rules; and U(1)'s audio, plan and procedure; a change after that point shall void the run.
- [ ] **TXG-QUAL-019**: The tier 5 run shall measure and report, for each capture, the call, transaction, per-kind and per-cell figures and the transient peak.
- [ ] **TXG-QUAL-020**: The first A40 run with transaction graphs on, at 80 and at 160 ms, shall record for both captures the call, transaction and per-kind totals, the transient peak, `m`, `r`, the absorbed rounding and the capture time, for `N` = 16, 32 and 64 at `max_num_seqs` 64.
- [ ] **TXG-QUAL-021**: An installed-engine check with a profiled budget shall show that core's logged graph-memory estimate exceeds `B_hook`'s by at least the profiling transaction total (both estimates include one charged margin, REG-MEM-020 and TXG-MEM-004), within the run-to-run spread of two `B_hook` startups, which the check reports; that the serving call total is at most the profiling call total; and shall report, without bounding it, the KV budget difference against `B_hook`.
- [ ] **TXG-QUAL-022**: An installed-engine check under a fixed `--kv-cache-memory-bytes` shall show the uncharged-memory WARNING of TXG-MEM-008 with its figures in the startup log, and a check with the profiling capture suppressed where TXG-MEM-007 requires it shall show startup failing.

## System model

- [ ] **TXG-MODEL-001**: The repository shall carry TLA+ models of the transaction-graph capture lifecycle on the hook and the split step under `models/transaction-graph/`, one specification and configuration file per checked model, each with a header stating the TLC version and what each invariant means.
- [ ] **TXG-MODEL-006**: Every change to the transaction-graph capture lifecycle (a hook's behaviour, an ordering rule, a failure path) shall update the models under `models/transaction-graph/` in the same change.
- [ ] **TXG-MODEL-002**: The models shall cover one worker with a small `N` and bounded steps, with actions for every hook call of the capture lifecycle in core's startup order, each cell capture able to fail, the memory comparison able to overrun, `clear_cudagraphs` also after a failed or skipped capture, a second serving capture attempt after a successful and after a failed serving capture, `shutdown` from any state, scheduled steps (one-kind replay, split replay, counted fallback, pre-launch failure, a failing cancel of the held reservation before the first launch, failure at the first launch, between the launches or at the stage, a stage that raises before and one that raises after publication, and a declined step's option-off reservation, scatter and stage each able to fail), a step before post-warmup verification after which the engine may die, all-failed bypass steps on an unlatched worker, before and after verification, and on a latched worker (TXG-FAIL-009, TXG-FAIL-010), cleanup-only steps, dummy steps, and a nondeterministic choice of whether a profiling capture is required (including a budget fixed or an extensible cache disabled after construction) and whether it runs.
- [ ] **TXG-MODEL-003**: The models shall check the invariant that no cell is replayed outside a scheduled step after a passed verification, other than a capture's validation replay of rejected rows inside its `capture_cudagraphs` call.
- [ ] **TXG-MODEL-007**: The models shall check the invariant that no step replays a cell over profiling pools; a capture's validation replay of rejected rows inside the profiling `capture_cudagraphs` call is not a step replay.
- [ ] **TXG-MODEL-008**: The models shall check the invariant that nothing from the profiling pools, the margin included, is retained after `clear_cudagraphs` returns.
- [ ] **TXG-MODEL-009**: The models shall check the invariant that at most one serving capture captures graphs in a worker.
- [ ] **TXG-MODEL-010**: The models shall check the invariant that a serving capture with no profiling capture before it is either reported uncharged because none was required or fails startup.
- [ ] **TXG-MODEL-011**: The models shall check the invariant that a serving capture that retains more than its profiling capture fails startup.
- [ ] **TXG-MODEL-012**: The models shall check the invariant that each commit reservation, a covered step's and a declined step's option-off reservation alike, is resolved by exactly one successful stage or one cancel (TXG-EXEC-010): a stage that raises before it publishes the reservation to the sink's collection leaves it cancellable, a cancel after a successful stage is a no-op, and after a worker-fatal failure it remains unresolved only if its cancellation failed, no later step that schedules a row then completing.
- [ ] **TXG-MODEL-013**: The models shall check the invariant that a step whose first launch ran never falls back and never stages after a failure.
- [ ] **TXG-MODEL-014**: The models shall check the invariant that after a latch no step that schedules a row completes, an all-failed bypass step included, and that an all-failed bypass step replays no cell, increments no fallback counter and holds no reservation; a cleanup-only step (REG-MEM-014) may complete.
- [ ] **TXG-MODEL-015**: The models shall check the invariant that after any failure in a capture call, nothing that call created (segment graphs, cells, buffers, margin) remains captured.
- [ ] **TXG-MODEL-016**: The models shall check the invariant that after `shutdown` nothing remains captured.
- [ ] **TXG-MODEL-004**: The models shall check, under fairness, that every latched or failed worker reaches `shutdown` under cooperative teardown (a worker that runs the runner's shutdown), and that every startup whose construction succeeded and that is neither shut down cooperatively nor killed before it serves eventually serves or fails with a reported error; they shall claim no property for a killed worker or a failed construction.
- [ ] **TXG-MODEL-005**: TLC shall check every model under `models/transaction-graph/` without violations on the revision a tier 5 claim names.
